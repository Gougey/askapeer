## 1. Cross-epic conflicts and gaps

These are the items most worth discussing as a group, since a decision on one may constrain the others.

### 1.1 `member_interests` vs. `community.follows` — possible duplicate concepts (NARROWED 2026-07-17)

EPIC-I's `community.member_interests` (a *weighted* interest signal used to score research-article relevance) and EPIC-B's `community.follows` with `target_type = tag` (a *binary* follow relationship, resolved 2026-07-14 — see Section 2) are both, conceptually, "a member's interest in a topic."

**Narrowed by the taxonomy resolution (§1.2, 2026-07-17)**: the *vocabulary* both reference is now unified (one `community.tags`), which was the substance of the duplication worry — a member's forum tag-follows and research-feed interests are drawn from the same list. What remains open is only whether the two *relationship mechanisms* (weighted vs. binary) should collapse into one. They serve different scoring needs, so keeping both is defensible; this is now a smaller, separable call, not a blocking conflict.

**Needs**: a deliberate choice on the mechanism question — low-stakes, non-blocking (both can be built independently).

*Source: EPIC-I spec §4.*

### 1.2 Taxonomy unification (three unreconciled vocabularies) — RESOLVED 2026-07-17

**Resolved** (Andrew Renshaw's input) — see Section 2 (taxonomy entry) for the full record. The three vocabularies are collapsed into **one controlled `community.tags` table**, faceted (`region`/`muscle`/`structure`/`pathology`) with a region grouping and a `synonyms` array, used by **both** the forum and the research feed. Categories are **content type**; body areas and clinical terms are **tags**; **OSIICS omitted**; **MeSH** kept only as an internal `mesh_id` mapping. Full decision + agreed seed list in `docs/2026-07-17-taxonomy-standards-research.md`. *(Heading kept in place so cross-references to "§1.2" resolve.)*

*Source: EPIC-C spec §2, §3, §12; EPIC-I spec §4, §5, §9; EPIC-J spec §4; architecture spec §4.2; taxonomy-standards research note.*

### 1.3 Moderator-forced handle rename — where does it live? — RESOLVED 2026-07-17

**Resolved** (Adrian's nod) — the moderator-forced rename lives in **EPIC-F's `rename_handle` action type**, not a bespoke EPIC-B endpoint. A moderator-initiated rename is a moderation action in substance; EPIC-B retains only the `handle_name_history` audit table and the blocklist/uniqueness validation (its §3/§5/§6) that EPIC-F's action re-runs on the new name. EPIC-B's Section 5 rename endpoint is superseded. *(Heading kept in place so cross-references to "§1.3" resolve.)*

*Source: EPIC-B spec §5/§6/§13, EPIC-F spec §3/§10.*

### 1.4 Two independent access-control gates: moderation status and billing status — RESOLVED 2026-07-17

**Resolved** — see Section 2 (EPIC-H entry). Community access is governed by **two independently-checked gates** — `community.handles.status` (EPIC-B/F moderation) **and** `billing.subscriptions.status` (EPIC-H) — not one combined flag, because a moderation suspension (resolved by appeal) and a billing lapse (resolved by paying) are different in kind. The billing-lapsed token reuses EPIC-A's pending-token scoping pattern. Architecture spec §5.2 amended. *(Heading kept in place so existing cross-references to "§1.4" resolve; full reasoning in Section 2.)*

*Source: EPIC-H spec §4.*

## 2. Already resolved

- **Follow targets, revisited — resolved 2026-08-06 and 2026-08-08.** Supersedes the tag-follow entry below, which remains as the record of what was decided in July. Two changes, both narrowing. **(1) Tag-following retired (6 Aug):** `community.member_interests` (EPIC-I, built at S8b) already asks members which parts of the taxonomy they care about — weighted, subtree-expanded, with a picker over all 588 nodes in front of them — so a second *binary* copy of the same choice would have been a parallel answer to a question already asked, drifting from the first and requiring the tag picker to be built a third time. `target_type` became `enum(handle, post)`, and **post-following was built** (S15, migrations `0027`/`0028`). **(2) Handle-following not required (8 Aug, on review):** deferred rather than deleted; the unused `handle` enum value stays so revisiting costs no migration. ⚠️ **The knock-on is the substantive part**: tag-follows and handle-follows were the *only* two inputs to EPIC-C §8's personalised Discussions feed, so that feature is now **hollowed out rather than deferred** — it has nothing left to select on, and reviving it means designing it afresh from the one interest signal members actually give us. The trending view survives as a standalone ordering, no longer a fallback. EPIC-G's weekly digest ("top-kudos content in followed tags") likewise needs redefining rather than merely implementing. *(PRD §6.1 Should-have note; EPIC-B spec §8; EPIC-C spec §8/§9; `docs/2026-08-06-post-follow-design.md`.)*
- **The missing tag-follow mechanism — resolved 2026-07-14.** Three PRD features assumed a member could "follow a tag" — EPIC-C's Should-have personalised feed ("tags **and handles** followed"), EPIC-G's Should-have email digest ("top-kudos content in **followed tags**") — but EPIC-B originally only specified `community.handle_follows` (following a *handle*), not a tag equivalent. **Adrian asked**: what's the recommendation, and are handles and tags being confused as the same thing? **Answer**: they're not the same thing (a handle is *who*, a tag is *what*) — the PRD itself already treats "follow" as one verb applying to both target types, so there's no need for separate terminology. The real duplication risk was three separate "interest" mechanisms (handle-follows, a not-yet-built tag-follow, and EPIC-I's weighted `member_interests`), not the handle/tag distinction itself. **Decision**: generalise EPIC-B's `community.handle_follows` into a single `community.follows` table (`follower_handle_id`, `target_type` enum of `handle`/`tag`, `target_id`) — the same `target_type`/`target_id` discriminator pattern already used by `community.kudos` and `community.reports`, not a new modelling idiom. EPIC-B keeps ownership (it already owned the narrower table and the follow endpoints); EPIC-C's personalised feed (now specified, its spec §8) and EPIC-G's weekly digest (its spec §7) are read-only consumers filtering `WHERE target_type = 'tag'`. `member_interests` (EPIC-I) remains a deliberately separate, weighted mechanism — whether *that* should eventually be unified with `community.follows` is its own still-open question (Section 1.1, above). *(EPIC-B spec §8/§9/§13; EPIC-C spec §8/§9/§12; EPIC-G spec §7/§11; EPIC-I spec §4/§9.)*
- **The expulsion/re-registration gap — resolved 2026-07-14.** `identity.members.verification_status` (EPIC-A) had no `expelled` value, while `community.handles.status` (EPIC-B) does — so when EPIC-F's `expel` action set a handle to `expelled`, nothing updated the identity-side status, and as specced a permanently expelled practitioner could re-register with the same professional credentials and get a brand-new handle. **Adrian's decision**: add an `expelled` value to `identity.members.verification_status`; if an expelled member attempts to re-register, the attempt must be prevented *and* logged/reviewed, not just silently rejected. Implemented as: the architecture spec's `identity.members` schema now includes `expelled` (Section 4.1, amended); EPIC-F's `expel` action writes both `community.handles.status = expelled` and an `identity.verification_decisions` transition to `expelled`, atomically (its spec, §3, §7); EPIC-A's existing uniqueness constraint blocks any non-`rejected` status by construction, so `expelled` is covered automatically, and a blocked attempt now additionally writes to a new `identity.reapplication_attempts` table, surfaced via `GET /v1/admin/reapplication-attempts` for admin review (EPIC-A spec, §2, §6, §8). One related sub-question remains open — see EPIC-F's per-epic list in Section 3, and the exact applicant-facing rejection wording — see EPIC-A's per-epic list in Section 3. *(Architecture spec — amendment note above §1; EPIC-A spec §2/§6/§8/§10/§11; EPIC-B spec §10/§13; EPIC-F spec §3/§7/§9/§10.)*
